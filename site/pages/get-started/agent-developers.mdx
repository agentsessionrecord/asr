---
title: "For agent developers"
description: "Export your agent's sessions as ASR, or convert its existing logs."
---

A converter can read your agent's native logs after each session, or the agent can export Agent Session Record (ASR) itself, with an export command or a file written next to its native log. Both produce the same records.

Start by mapping one saved native log by hand. The [Claude Code worked example](/agents/claude-code#worked-example) shows native lines beside the ASR they produce, and the [writer libraries](/tools/record#writer-libraries-and-shared-recorder-cores) serialize records from facts you supply.

## Write the header

The first record is the `session` header. Copy the native `sessionId` exactly. For `agent.name`, use the short name from the [agent list](/agents) or a reverse-DNS name under a domain you control, and add `namespace` only if session IDs can repeat across installations. Set `producer.method` to `native` for the agent's own export, `converter` for a tool that reads logs later, or `recorder` for a live observer, and name the native format in `producer.source`.

## Write messages and tool calls

Write completed items in source order. Keep native record IDs when they're unique, and otherwise derive stable IDs from native IDs or positions. Set a message's `author` only when the source says who wrote it, since a `user` role alone doesn't mean a person typed it.

Link each `tool_call` to its `tool_result` with `callId`, with at most one result per call ID. Write an `inference` record only for a model call the log records, and keep the served model separate from the requested one. Other useful native details can go in `_meta` under a reverse-DNS key.

## Add edits and commits

Write one `file_change` per changed file, with the path, the edit text and the `callId` of the tool that made it. Mark it `applied` only when the log shows the edit happened. Write a `vcs` record only for a commit the agent made, not one mentioned in a reply. If Git printed a short ID, store it in `commitPrefix` and leave out parents you don't know. Keep records copied from another session marked as copies so they aren't counted twice. See [Records](/spec/records) and [Code links and blame](/spec/code).

## Declare what's missing

List known losses in the header's `missing`, or in a later `session_info.missing` when a live writer finds one mid-session. Write a `gap` where history is missing, set `truncated: true` on shortened text, and leave out any time, model, cost or exit code you don't have. A compaction summary gets `origin: "compaction"`, followed by a `gap` if compaction destroyed history. Exclude known secrets, since passing validation doesn't make a file safe to share.

## Record what only the running agent knows

An agent writing ASR as it runs can record facts a converter usually can't recover. Write each one where it happens:

- each `approval` decision, with who decided and how long the grant lasts, and the `approvalId` on the result that followed it
- `session_info.agentSettings` at the start and at each change, with your own `mode`, `approval` and `sandbox` values verbatim
- the offered tools in `session_info.tools`, and instructions as messages with `origin: "instructions"`
- the settings each model call sent, in `inference.settings`
- `origin: "scheduled"` or `"external"` for runs started by a schedule or an outside event
- subagent links, with `tool_call.subagent` in the parent and `parent` in the child's header

Record only what the agent established. Don't infer an approval from a tool's outcome or a permissive mode, and record a reused grant as `by: "policy"`. [Records](/spec/records) defines each field.

## Validate and publish the mapping

```sh
node tools/validator/bin/asr-validate.js sample.jsonl
```

The validator checks structure and links, not whether the export matches the source, so compare the messages, tools and edits with the native file yourself. Publish the sample and the source versions the mapping supports, using the [converter notes template](/agents#converter-notes-template).

You have a first converter when a sample validates and a reader can follow its edit back to the prompt. A source with no edit evidence can still support search if it lists `file_changes` in `missing`.

The [integration guide](/guides/integration) describes an export command and a discovery file, and the [ACP recording guide](/guides/acp) covers recording a live editor connection.
